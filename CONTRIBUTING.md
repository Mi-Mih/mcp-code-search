# 🛠️ Разработка code-search

Этот документ описывает локальный цикл разработки и проверки изменений. Устройство
системы и её инварианты изложены в [архитектурной документации](docs/ARCHITECTURE.md).

## ✅ Требования

- Python 3.10 или новее;
- SQLite 3.43 или новее;
- Ollama и `bge-m3` только для интеграционных прогонов индексации/поиска;
- dev-зависимости из `requirements-dev.txt` для тестов, Ruff, mypy и eval.

Создание окружения:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
```

Рабочий MCP-сервер runtime-зависимостей не имеет и запускается системным Python.
Виртуальное окружение нужно только разработчику.

## 🧪 Быстрые проверки

Перед отправкой изменения выполните:

```bash
.venv/bin/ruff check .
.venv/bin/mypy
.venv/bin/pytest
```

Тесты изолируют сеть и Ollama через fake-эмбеддеры. Реальная модель нужна для
ручного end-to-end прогона и измерения качества.

## 🗂️ Структура репозитория

```text
code_search/          библиотека, CLI и MCP-сервер
eval/                 харнесс, пример разметки и агрегаты измерений
tests/                модульные и протокольные тесты
docs/                 архитектура и справочник интерфейсов
README.md             назначение, качество и обзор использования
SETUP.md              пошаговая установка для пользователя
CONTRIBUTING.md        цикл разработки
```

`main.py` — шаблонный файл IDE и не является точкой входа проекта. Поддерживаемые
точки входа запускаются через `python -m code_search.<module>`.

## ✍️ Правила изменений

- Сохраняйте stdlib-only runtime: новая обязательная зависимость меняет один из
  базовых принципов проекта и должна быть явно обоснована.
- Не печатайте в `stdout` из серверного пути — этот поток зарезервирован JSON-RPC.
- Не изменяйте `Chunk.text`; enrichment должен храниться отдельно.
- При изменении границ нарезки увеличьте `CHUNKER_VERSION` и добавьте regression-test.
- При несовместимом изменении SQLite увеличьте `SCHEMA_VERSION` и протестируйте
  понятный отказ от старого индекса.
- Публичные функции и классы должны иметь docstring; сложные решения объясняйте
  рядом с кодом через причину и инвариант, а не пересказ операции.
- Новые Markdown-разделы оформляйте с подходящим emoji в заголовке.

## 🧭 Добавление языка

Без парсера язык уже можно подключить через `--suffix .ext`: он получит generic
нарезку по блокам. Для специализированной поддержки:

1. добавьте функцию нарезки и зарегистрируйте расширение в `_CHUNKERS`;
2. проверьте непересечение и полное покрытие значимых строк;
3. добавьте тесты символов, oversized-блоков и детерминизма;
4. увеличьте `CHUNKER_VERSION`, если меняются сохранённые границы;
5. измерьте качество на размеченных запросах для этого языка.

## 📊 Измерение поиска

Сначала соберите индекс целевого проекта, затем подготовьте YAML по образцу
[`eval/queries.example.yaml`](eval/queries.example.yaml):

```bash
.venv/bin/python eval/harness.py /путь/к/проекту \
  --queries /путь/к/queries.yaml --save /tmp/results.json
```

Не подбирайте параметры по holdout-набору. Харнесс требует `--unblind` для файлов
с `holdout` в имени; этот флаг фиксирует осознанный одноразовый прогон, а не делает
повторные запуски методологически безопасными.

## 🔌 Проверка MCP

Минимальный smoke-test без клиента:

```bash
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"0"}}}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}' \
  | PYTHONPATH=. .venv/bin/python -m code_search.server --root /путь/к/проекту
```

В `stdout` должны быть только две JSON-строки. Баннер допустим только в `stderr`.
