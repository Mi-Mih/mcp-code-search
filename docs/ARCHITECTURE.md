# 🏗️ Архитектура code-search

Этот документ описывает границы компонентов, путь данных и инварианты, которые
важно сохранить при изменениях. Инструкции по запуску находятся в
[SETUP.md](../SETUP.md), а справочник интерфейсов — в [API.md](API.md).

## 🧭 Карта компонентов

| Модуль | Ответственность | Основные сущности |
|---|---|---|
| `code_search.corpus` | Выбор файлов и обнаружение изменений | `FileState`, `list_files`, `content_hash` |
| `code_search.chunker` | Нарезка исходников на независимые фрагменты | `Chunk`, `chunk_text`, `enrich`, `fts_text` |
| `code_search.embedder` | HTTP-клиент Ollama и нормализация векторов | `Embedder`, `ModelSpec` |
| `code_search.store` | Схема SQLite, метаданные и атомарная запись | `StoredChunk`, `open_index`, `replace_file` |
| `code_search.indexer` | Планирование и выполнение индексации | `Plan`, `IndexStats`, `reindex` |
| `code_search.search` | BM25, векторный поиск и Reciprocal Rank Fusion | `Searcher`, `SearchResults`, `Hit` |
| `code_search.refresh` | Проверка актуальности и фоновое обновление | `Refresher`, `Status` |
| `code_search.server` | MCP поверх JSON-RPC 2.0 и stdio | `Server`, `ToolResult` |
| `eval.harness` | Измерение Recall, MRR, задержки и бюджета ответа | `Query`, `Outcome`, `report` |

Зависимости направлены от внешних входов к небольшим внутренним слоям:

```text
MCP-клиент
    │ JSON-RPC/stdin/stdout
    ▼
server ──► refresh ──► indexer ──► corpus ──► chunker
   │                       │                       │
   │                       ├────────► embedder ◄───┘
   │                       ▼
   └────────► search ───► store ◄──────── SQLite
                  │
                  └─────────────► embedder ─────► Ollama
```

## 📥 Путь индексации

1. `corpus.list_files` получает tracked и untracked файлы через Git с учётом
   `.gitignore`; вне Git используется рекурсивный обход.
2. `indexer.plan` сравнивает `mtime_ns` и размер с сохранённым состоянием. Хеш
   читается только для кандидатов на изменение.
3. `chunker.chunk_text` выбирает специализированную нарезку для Python,
   Markdown и reStructuredText. Дополнительные расширения режутся по блокам.
4. `chunker.enrich` добавляет путь, символ, сигнатуру и docstring к тексту для
   эмбеддинга; исходный `Chunk.text` остаётся дословным фрагментом файла.
5. `Embedder.embed_documents` отправляет батчи в Ollama и L2-нормализует векторы.
6. `store.replace_file` атомарно заменяет файл, чанки, FTS-строки и векторы.

Индекс хранится в `<root>/.code-search/index.sqlite`. Настройки модели, размерность
вектора, версия схемы, версия чанкера и дополнительные расширения записываются в
таблицу `meta`.

## 🔎 Путь запроса

1. `Server.search_code` валидирует аргументы MCP-инструмента.
2. `Refresher.ensure_fresh` быстро сообщает об устаревании и при необходимости
   запускает один фоновый refresh; текущий запрос не ждёт полной индексации.
3. `Searcher.search` строит одну или две независимые выдачи:
   - `lexical` — FTS5/BM25 по безопасно токенизированному выражению;
   - `vector` — скалярное произведение нормализованных векторов;
   - `hybrid` — слияние рангов через Reciprocal Rank Fusion.
4. SQLite загружает полные чанки только для итоговых идентификаторов.
5. `_split_by_budget` оставляет первые результаты с текстом, а хвост возвращает
   как ссылки `path:start-end`, не нарушая ранжирование и значение `k`.
6. MCP-клиенты новой версии получают одновременно текст и `structuredContent`;
   старые клиенты получают только текстовый формат.

## 🗄️ Модель данных

В SQLite используются три логические набора данных:

- `files` — путь, stat и короткий хеш содержимого;
- `chunks` — строки, символ, тип, исходный текст, FTS-текст и бинарный вектор;
- `meta` — версии форматов и параметры, определяющие совместимость индекса.

`chunks_fts` — contentless FTS5-таблица. Триггеры синхронизируют её с `chunks`.
Идентификатор чанка объявлен `AUTOINCREMENT`: удалённый ID нельзя выдать другому
чанку, пока старый `Searcher` ещё держит в памяти предыдущий набор векторов.

## 🔒 Ключевые инварианты

- `stdout` MCP-сервера содержит только JSON-RPC; диагностика идёт в `stderr`.
- `Chunk.text` никогда не обогащается и остаётся точной выдержкой из файла.
- Границы строк 1-based и включают обе границы.
- Число чанков обязано совпадать с числом векторов при записи файла.
- FTS-индекс меняется только через триггеры основной таблицы.
- Размерность модели, версия схемы и версия чанкера проверяются перед поиском.
- Дополнительные расширения сохраняются в индексе, чтобы фоновый refresh не
  исключил ранее добавленный язык.
- При устаревшем индексе поиск остаётся доступным и явно выставляет `stale: true`.
- Одновременно выполняется не более одного фонового refresh на процесс сервера.

## ♻️ Актуальность и конкурентность

Проверка изменений трёхступенчатая: неизменившиеся stat-поля не требуют чтения;
изменившийся stat при прежнем хеше обновляет только метаданные; новый хеш приводит
к повторной нарезке и эмбеддингу файла. Удаления чистятся отдельно.

SQLite работает в WAL-режиме, поэтому поиск может читать индекс во время записи.
После успешного refresh `Searcher.invalidate` сбрасывает кэш векторов. Несколько
отдельных MCP-процессов могут читать один индекс, но одновременные записи между
процессами не координируются приложением и могут получить SQLite busy timeout.

## 🧪 Контроль качества

Модуль `eval/harness.py` прогоняет каждый размеченный запрос в режимах `lexical`,
`vector` и `hybrid`, затем считает Recall@1/3/5/10 и MRR@10. Пример разметки —
[`eval/queries.example.yaml`](../eval/queries.example.yaml), сохранённые агрегаты —
[`eval/holdout_results.json`](../eval/holdout_results.json).

Изменения границ чанков требуют увеличить `CHUNKER_VERSION`; несовместимые
изменения таблиц — `SCHEMA_VERSION`. Изменение MCP-контракта должно сопровождаться
тестами для актуальной и старых поддерживаемых версий протокола.

## ⚠️ Осознанные ограничения

- Полноценный синтаксический разбор есть только для Python.
- Поиск требует локальную Ollama для векторного и гибридного режимов.
- Векторный индекс полностью загружается в память процесса.
- Автоматическое обновление eventual-consistent: один запрос может увидеть старые
  результаты, но получает признак `stale` и хеши файлов.
- Сервер реализует нужное подмножество MCP напрямую, а не через SDK.
