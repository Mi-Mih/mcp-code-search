# 🔎 code-search — семантический поиск по коду через MCP

MCP-сервер, который отвечает на вопросы вида «где в коде инвалидируется кэш?» —
то есть на вопросы, где вы **не знаете, как искомое названо**. Для точных
идентификаторов остаётся grep: он для этого лучше, и сервер прямо говорит об этом
модели в описании инструмента.

Сервер клиент-нейтрален: это обычный MCP поверх stdio, и подключается он к любому
клиенту протокола — Claude Code, Cursor, Codex CLI. Индекс один на всех, тексты
инструментов не ссылаются на инструменты конкретного клиента.

Работает локально: эмбеддинги считает Ollama на вашей машине, индекс лежит в SQLite
внутри проекта. Наружу ничего не уходит.

Зависимостей нет — только стандартная библиотека Python. Ни `numpy`, ни `requests`,
ни SDK `mcp`: всё, что понадобилось, оказалось дешевле написать (`urllib` для Ollama,
`array` + `memoryview` для векторов, ~120 строк JSON-RPC для протокола), чем тащить
зависимость в окружение, где `pip` закрыт PEP 668.

## 🎯 Зачем он, если есть Grep

Сравнение на 40 отложенных запросах к боевому проекту — здесь и далее `Project1`
(241 файл, 3044 чанка).
Запросы естественно-языковые, поэтому «паттерн» для grep — это дизъюнкция значимых
слов запроса (`grep -rlEi "слово1|слово2|..."`), то есть режим максимальной полноты.

| | находит нужный файл | файлов в выдаче (медиана) | ~токенов, если всё прочитать |
|---|---|---|---|
| `grep`, все слова через OR | **0.85** | 81 | **~800 000** |
| `grep`, все слова через AND | 0.10 | 0 | — |
| `search_code`, k=15 | **0.75** | 15 | **~5 400**¹ |

¹ Медиана полного текста всех 15 хитов на момент замера. С тех пор выдача сжата:
полный текст идёт, пока укладывается в бюджет 3000 токенов, остальные хиты —
однострочными ссылками `path:строки`, то есть реальное чтение теперь ~3 k, а все
15 хитов остаются видимыми.

Полнота у grep даже **выше** — и всё равно это бесполезно, потому что **у него нет
ранжирования**. Нужный файл действительно лежит где-то среди этих 81, но прочитать
их целиком — это ~800 k токенов: вчетверо больше стандартного окна в 200 k. Сузить
через AND нельзя: естественно-языковой запрос содержит слова, которых в коде нет
вообще, и AND схлопывает выдачу в ноль на 90% запросов.

Семантический поиск покупает не полноту, а **порядок**: тот же ответ в 15
отсортированных фрагментах вместо 81 неотсортированного файла. Это ~150-кратная
разница в объёме чтения при сопоставимом попадании — 0.75 против 0.85.

Обратная сторона, тоже измеренная: на точных идентификаторах grep выигрывает.
Там медиана его выдачи — **4 файла**, ранжирование не нужно, и лишний круг через
эмбеддинги только теряет время. Поэтому в описании инструмента написано прямым
текстом «для точных идентификаторов используй лексический поиск (grep)», и это не
вежливость, а способ не дать модели гонять через семантику всё подряд. Формулировка
намеренно называет способность, а не инструмент конкретного клиента: в Claude Code
это Grep, в Cursor и Codex — их собственные поисковые инструменты.

### 📊 Качество ранжирования

Замер на том же отложенном наборе, Recall@10 — доля запросов, где нужный файл попал
в первую десятку. Baseline (BM25) был зафиксирован **до** замеров, вместе с порогом
приёмки «+15 п.п. на концептуальных запросах».

| вид запроса | n | BM25 | только вектор | **гибрид** |
|---|---|---|---|---|
| concept — «где инвалидируется кэш» | 24 | 0.54 | 0.83 | **0.83** |
| domain — термины предметной области | 6 | 0.33 | 0.83 | **0.83** |
| docs — вопросы к `.rst` | 4 | 0.50 | 0.75 | **0.75** |
| exact — точный идентификатор | 2 | 1.00 | 0.50 | **1.00** |
| test — «где это тестируется» | 4 | 0.00 | 0.00 | **0.00** |
| **все** | **40** | **0.47** | 0.72 | **0.75** |

Порог пройден с запасом: **+29.2 п.п.** на концептуальных запросах против BM25.

Что здесь стоит прочитать честно:

- **Запросы к тестам не работают.** 0.00 во всех режимах, воспроизводимо. Это
  известный незакрытый провал, а не шум; он один стоит 8 п.п. общей полноты
  (без него общий Recall@10 = 0.83). Чинить его по этим числам уже нельзя — набор
  отыгран, нужен отдельный размеченный набор запросов к тестам.
- **Гибрид выигрывает у чистого вектора узко.** +3 п.п. общей полноты и ровно ноль
  на концептуальных. Вся его ценность — страховка: на точных идентификаторах
  (1.00 против 0.50) и на редких полных промахах вектора. MRR у гибрида стабильно
  ниже, чем у вектора, и это осознанный размен: выдачу читает Клод, он читает все k
  результатов, поэтому Recall@k отражает пользу, а MRR — почти нет.
- **Размен из предыдущего пункта держится на `k`, и это стоит записать как условие.**
  На малых k гибрид не «узко выигрывает», а проигрывает: Recall@1 — 0.30 против
  0.425 у вектора, Recall@5 — 0.65 против 0.70. Оправдание «Клод всё равно читает
  все k» верно ровно пока `DEFAULT_K = 15`. Если выдачу когда-нибудь сузят до
  k ≤ 5, правильным режимом станет `vector`, а не `hybrid`.

Латентность запроса: **p50 145 мс, p95 166 мс**. Больше половины — это Ollama,
считающая эмбеддинг самого запроса.

## 🚀 Установка

**Нужно:** Python 3.10+, SQLite 3.43+ (для `contentless_delete`; проверяется при
старте), [Ollama](https://ollama.com) с моделью `bge-m3`.

```bash
ollama pull bge-m3       # ~1.2 ГБ, 1024 измерения
ollama serve             # если не запущена как сервис
```

Сервер и индексатор запускаются системным Python — виртуальное окружение не нужно.

### 1. 🗂️ Собрать индекс

```bash
cd /путь/к/code-search
python3 -m code_search.indexer /путь/к/проекту
```

Это долго и делается один раз: **~40 минут на 61 k строк** (241 файл → 3044 чанка,
скорость упирается в Ollama, ~1.2 чанк/с). Прогресс с ETA печатается по файлам,
каждый файл коммитится отдельной транзакцией — прервать `Ctrl-C` и продолжить позже
безопасно, уже проиндексированное не потеряется.

Полезное перед долгим прогоном:

```bash
python3 -m code_search.indexer /путь --dry-run     # что будет переиндексировано
python3 -m code_search.indexer /путь --exclude 'extern/*' --exclude 'airflow/*'
python3 -m code_search.indexer /путь --suffix .ts  # добавить ещё один язык
python3 -m code_search.indexer /путь --rebuild     # снести индекс и собрать заново
```

Индекс кладётся в `<проект>/.code-search/index.sqlite` вместе с `.gitignore`,
который его прячет. Для 3044 чанков это 22 МБ на диске, из них ~12 МБ векторы.

Индексируются `.py`, `.rst`, `.md` — только файлы, известные git
(`git ls-files` плюс untracked с учётом `.gitignore`); без git — обход каталога.
`node_modules`, `__pycache__`, `site-packages` и подобные отсекаются всегда.
Сколько файлов отброшено по расширению, индексатор печатает всегда — чтобы
на смешанном проекте пробел не приходилось угадывать по числу файлов:

```
пропущено по расширению: 813 файл(ов) — .ts 402, .html 231, .scss 118, ...
  чтобы добавить язык: --suffix .ts (обобщённая нарезка, см. README)
```

### 1a. 🌐 Языки, кроме Python

`--suffix .ts` (флаг повторяемый) добавляет расширение в корпус. Такие файлы
режутся **обобщённо** — по блокам, разделённым пустыми строками, с набивкой до
512 токенов. Работает для любого языка с фигурными скобками, но парсера нет,
поэтому у чанка не будет ни имени функции, ни сигнатуры, ни докстринга — а это
как раз то, чем живёт обогащение (`enrich`) и лексическая ветвь. Гранулярность
тоже грубее: небольшой файл целиком станет одним чанком, тогда как `.py`
дал бы чанк на метод.

Настройка **запоминается в индексе**, а не живёт в командной строке. Иначе
фоновое обновление, которое запускает MCP-сервер (он про флаги не знает),
сочло бы все `.ts` удалёнными и молча вычистило бы их при первом же запросе.
Поэтому:

- добавить язык — `--suffix .ts`, стоит одну индексацию новых файлов, остальные
  сохраняют векторы;
- отказаться — `--suffix none`, стоит только удаления;
- `--rebuild` без `--suffix` возвращает набор к умолчанию.

Сгенерированные бандлы обобщённая нарезка отклоняет: файл, в котором есть строка
длиннее 5000 символов, не режется (внутри строки границу поставить нечем) и дал бы
один чанк на два мегабайта. Такие файлы попадают в индекс с нулём чанков, и
индексатор их считает отдельной строкой в итоге.

Мер качества для не-Python нет ни одной: все числа выше получены на питоновском
проекте. Ожидание — что будет хуже, чем на `.py`, но насколько, неизвестно.

### 2. 🔌 Подключить к Claude Code

MCP-серверы задаются не в `settings.json`, а в `.mcp.json` в корне проекта:

```json
{
  "mcpServers": {
    "code-search": {
      "command": "/usr/bin/python3",
      "args": [
        "-m", "code_search.server",
        "--root", "/путь/к/проекту"
      ],
      "env": {
        "PYTHONPATH": "/путь/к/code-search",
        "PYTHONUTF8": "1"
      }
    }
  }
}
```

`--root` — проект, по которому ищем; `PYTHONPATH` — каталог, где лежит пакет
`code_search`. Проверить, что подключилось: `/mcp` в Claude Code.

**Интерпретатор указан абсолютным путём намеренно.** Claude Code запускает сервер
не из вашей интерактивной оболочки, и `python` в его `PATH` может не оказаться
вовсе — на этой машине, например, есть только `python3`. Абсолютный путь снимает
вопрос; заодно он гарантирует, что сервер поедет на системном Python, которому
достаточно стандартной библиотеки, а не на случайно активном окружении.

Проверить сервер до подключения, ровно тем же способом, каким его запустит клиент:

```bash
printf '%s\n' \
 '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"0"}}}' \
 '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"index_status","arguments":{}}}' \
 | PYTHONPATH=/путь/к/code-search \
   /usr/bin/python3 -m code_search.server --root /путь/к/проекту
```

Первая строка вывода уходит в stderr — это баннер. Всё остальное обязано быть
строками JSON: если в stdout попало что-то ещё, клиент увидит сервер сломанным.

**Альтернатива: подключить только себе.** `.mcp.json` лежит в репозитории и при
коммите уедет к коллегам, у которых ни пути к серверу, ни своего индекса нет.
Если сервер нужен лично вам, тот же блок кладётся в `~/.claude.json`, в
`projects["/путь/к/проекту"].mcpServers` — репозиторий тогда не трогается вовсе:

```jsonc
// ~/.claude.json
{
  "projects": {
    "/путь/к/проекту": {
      "mcpServers": {
        "code-search": { /* тот же блок, что выше */ }
      }
    }
  }
}
```

Ключ проекта должен совпадать с каталогом, из которого вы запускаете Claude Code,
**точно** — запуск из подкаталога сервера не подхватит.

### 2b. 🔗 Другие клиенты: Cursor, Codex CLI, любой MCP

Команда запуска везде одна и та же — различается только файл, куда её положить.
Индекс тоже один: все клиенты читают `<проект>/.code-search/index.sqlite`.

**Cursor** — `.cursor/mcp.json` в корне проекта (или `~/.cursor/mcp.json`
глобально), формат идентичен `.mcp.json` выше.

**Codex CLI** — `~/.codex/config.toml`:

```toml
[mcp_servers.code-search]
command = "/usr/bin/python3"
args = ["-m", "code_search.server", "--root", "/путь/к/проекту"]
env = { PYTHONPATH = "/путь/к/code-search", PYTHONUTF8 = "1" }
```

**Любой другой клиент MCP** — тот же `command`/`args`/`env` в его формате
конфигурации. Сервер поддерживает версии протокола 2024-11-05…2025-06-18 и
проверяется без клиента вообще — protocol-probe командой из предыдущего раздела.

JSON-RPC при этом читается по букве спецификации, а не «как получится»: `jsonrpc`
должен быть `"2.0"`, `id` — строкой или целым числом, явный `"id": null` — это
некорректный запрос с ответом `id: null`, а не уведомление, которое можно
проглотить; JSON-массив принимается как batch и отвечается одним массивом (в
2025-06-18 batch из MCP убрали, но клиент постарше его прислать может). Молчит сервер
только на уведомления — там молчание обязательно.

Оговорка про два клиента разом: чтения из SQLite безопасны, но если оба процесса
одновременно заметят устаревший индекс, два фоновых обновления будут толкаться
на записи (SQLite их сериализует, возможны busy-таймауты). При поочерёдной
работе это не проявляется.

### 3. ⌨️ Поиск без Claude, из консоли

Для ручной проверки выдачи:

```bash
python3 -m code_search.search /путь/к/проекту "где режутся markdown-заголовки" -k 5
python3 -m code_search.search /путь "..." --mode vector --path-glob 'src/pkg/*' --full
```

## 🧰 Инструменты

Их два, и это решение, а не недоделка: от широкого набора Клод начинает выбирать
наугад между похожими инструментами.

### 🔍 `search_code(query, k=15, path_glob=None)`

Ответ — не JSON, а текст: читает его модель, а не парсер, и у текста нет
ни повторяющихся ключей, ни скобок, ни JSON-эскейпов на каждом переводе строки
в возвращаемом коде. На медианном запросе k=15 это ~3.3 k токенов вместо ~6.4 k
у прежнего JSON-формата.

```
src/pkg/parser.py:12-48 parse_section
----
def parse_section(...):
    ...
----
src/pkg/cache.py:80-101 invalidate
----
...
----
ещё релевантное (текст не включён — прочитай указанный диапазон строк файла):
  src/pkg/store.py:44-70 save_chunk
  tests/test_cache.py:10-35 test_invalidate

hash: src/pkg/parser.py=3f9a12b04c71 src/pkg/cache.py=88d01e42aa90 ...
```

Результаты отсортированы сервером; никакой оценки в выдаче больше нет — прежний
`score` всё равно был ранжирующей величиной, несравнимой между запросами, и
ничего, кроме порядка, не сообщал.

Полный текст идёт, пока укладывается в бюджет **3000 токенов** (первый результат —
всегда с текстом, даже если он один превышает бюджет). Остальные хиты не
отбрасываются, а деградируют до ссылок `path:начало-конец символ` в секции «ещё
релевантное»: все k хитов остаются видимыми, а нужный диапазон дочитывается чтением
файла по указанным строкам (в Claude Code — Read). Это заменило прежний
`dropped_by_budget`, при котором срезанный хвост становился невидимым.

`hash:` в футере — первые 12 hex SHA-256 каждого упомянутого файла, один раз на
файл. Если правки шли прямо сейчас, сверить: `sha256sum <file> | cut -c1-12`.

`stale: true` (строка появляется в футере только когда это так) — рабочее
состояние, а не ошибка: индекс немного отстал от рабочей копии, ответ дан по
тому, что есть, фоновое обновление уже запущено.

`k` ограничен сверху 50. `path_glob` — GLOB по пути (`src/pkg/*`), фильтр
применяется к обеим ветвям поиска.

**Для программных клиентов** тот же ответ приходит и как данные: клиенту,
договорившемуся на протокол 2025-06-18, сервер кладёт в результат
`structuredContent` со схемой из `outputSchema` инструмента —

```json
{"results":    [{"path": "src/pkg/parser.py", "start_line": 12, "end_line": 48,
                 "symbol": "parse_section", "text": "def parse_section(...)"}],
 "references": [{"path": "src/pkg/store.py", "start_line": 44, "end_line": 70,
                 "symbol": "save_chunk"}],
 "stale": false,
 "file_hashes": {"src/pkg/parser.py": "3f9a12b04c71", "src/pkg/store.py": "88d01e42aa90"}}
```

Текст при этом не меняется и не сокращается: модель читает его, парсер берёт
структуру, и ни одному из них не нужно разбирать формат другого. Клиентам на
2025-03-26 и 2024-11-05 ни `structuredContent`, ни `outputSchema` не отправляются:
эти поля появились в одной ревизии спецификации, и более старый клиент не обещал
игнорировать незнакомые ключи.

### 📈 `index_status()`

```json
{"files": 241, "chunks": 3044, "model": "bge-m3", "chunker_version": "2",
 "stale_files": 0, "last_indexed": "2026-08-31T02:14:07",
 "refreshing": false, "last_error": null}
```

Про индекс, и только про него — состояние Ollama это отдельная вещь, и смешивать их
в одном поле значило бы врать. `last_error` — текст последнего сорвавшегося фонового
обновления (чаще всего «Ollama недоступна»), иначе `null`. Клиенту на 2025-06-18
тот же объект приходит и в `structuredContent`.

## 🏗️ Как это устроено

```
Claude Code
    │  MCP (stdio, JSON-RPC 2.0 построчно)
    ▼
server.py ──► search.py ──┬──► векторный поиск ──┐
    │                     │    (полный скан)     ├──► RRF ──► бюджет токенов
    │                     └──► BM25 (FTS5) ──────┘
    │
    └──► refresh.py ──► indexer.py ──► chunker.py ──► embedder.py ──► Ollama
                            │                                            │
                            └──────────► store.py (SQLite + FTS5) ◄──────┘
```

| файл | что делает |
|---|---|
| `server.py` | MCP поверх stdio: JSON-RPC, два инструмента, обработка отказов |
| `search.py` | две ветви поиска + слияние + бюджет токенов на выдачу |
| `refresh.py` | устаревание и фоновое обновление, инвалидация кэша векторов |
| `indexer.py` | оркестрация индексации, определение изменений, CLI |
| `chunker.py` | нарезка: AST для `.py`, заголовки для `.rst`/`.md`, пустые строки для остального |
| `embedder.py` | Ollama через `urllib`, батчи по 16, `keep_alive=30m` |
| `store.py` | схема SQLite, FTS5, векторы, метаданные и совместимость |
| `corpus.py` | перечисление файлов через git, дешёвое определение изменений |

### ✂️ Нарезка

`.py` режется по AST — по функциям и классам, слишком большие тела разбиваются
рекурсивно, всё остальное покрывается окнами. `.rst` и `.md` — по заголовкам.
Расширения, добавленные через `--suffix`, — по блокам между пустыми строками
(парсера нет, поэтому нет и имён символов).
Инварианты, которые проверяются и юнит-тестами, и полным прогоном по проекту:
`text` — дословный срез файла по `[start_line, end_line]`; чанки одного файла не
пересекаются; ни один не превышает 800 токенов; **каждая непустая строка попадает
хотя бы в один чанк** — последний означает, что из индекса ничего не выпадает молча.

Перед эмбеддингом чанк обогащается путём, именем символа, сигнатурой и docstring:
модель видит контекст, которого в самом фрагменте нет.

### 🔀 Две ветви и их слияние

Плотная ветвь находит код, который *означает* нужное, не разделяя с запросом ни
одного слова. Лексическая (BM25 поверх FTS5) находит тот самый идентификатор,
который плотная размазала. Каждая плоха там, где другая хороша, поэтому ни одной не
доверяем в одиночку.

Сливаются они **реципрокным слиянием рангов** — `1/(60 + ранг)`, просуммированное по
ветвям, — а не смешиванием оценок. Косинус и BM25 живут в несравнимых шкалах, и любая
взвешенная сумма требует константы нормализации, которую придётся перенастраивать при
каждом изменении корпуса. Рангам не нужно ничего.

Важная измеренная деталь: **в слияние идут только первые 3 ранга BM25**. Ниже них
BM25 — шум ровно на тех запросах, где плотная ветвь сильна, а слияние даёт этому шуму
полноценный голос. Подача всего пула BM25 в слияние стоила **13 п.п.** полноты на
концептуальных запросах. При этом в режиме `--mode lexical` BM25 работает на полную
глубину — иначе он был бы негоден как baseline для замеров.

Голова BM25 своё место отрабатывает: единственный запрос, который плотная ветвь
промахнула полностью (ранг 106), у BM25 стоит первым, и слияние возвращает его на
второе место.

### 🧮 Векторы

Полный скан на чистом Python: один непрерывный `array('f')`, срез `memoryview` на
чанк, `sum(map(operator.mul, ...))`. Замерено на 3044 × 1024: 20 мс загрузка,
130 мс на запрос. Ollama тратит на эмбеддинг самого запроса больше, так что ANN-индекс
оптимизировал бы не ту половину, а numpy (быстрее в ~40 раз) выкупил бы ~125 мс ценой
зависимости, которой в системном интерпретаторе нет. Пересмотреть стоит примерно на
30 k чанков.

### ♻️ Обновление индекса

Синхронного режима нет намеренно: 20 изменённых файлов — это ~3.5 минуты эмбеддинга,
а порог устаревания, достаточно малый, чтобы это скрыть от вызывающего, слишком мал,
чтобы оправдать вторую ветку кода. Правило одно: есть устаревшие файлы → отвечаем по
имеющемуся индексу, честно ставим `stale: true`, запускаем фоновое обновление.

Изменения определяются в три яруса, от дешёвого к дорогому:

| | |
|---|---|
| `mtime_ns` и размер не изменились | пропуск, файл даже не читается |
| изменились, хеш прежний | обновляется только `stat`, векторы остаются |
| хеш изменился | перенарезка и переэмбеддинг |

Только третий ярус стоит времени, и на обычной сессии правок он касается единиц
файлов. Второй — это `git checkout` той же версии, переформатирование в те же байты
или просто `touch`.

Второй ярус **закрывается прямо на пути запроса**: новый `stat` записывается обратно
первой же классификацией. Иначе он не закрывался бы никогда — переиндексация тоже
его закрывает, но она запускается только когда файл действительно изменился, а один
`touch` не делает индекс устаревшим. До этого `git checkout` на другую ветку и обратно
оставлял весь корпус в состоянии «stat разъехался», и **каждый** поиск заново читал и
хешировал его целиком: на `Project1` это 2 МБ чтения и 241 SHA-256 на запрос,
навсегда, пока кто-нибудь не запустит индексатор руками.

Смена модели эмбеддингов, размерности или версии чанкера делает индекс логически
несовместимым. Индексатор такой индекс пересобирает сам; **сервер отказывается его
открывать** и говорит, что запустить. Отказ здесь — не строгость: фоновое обновление
на несовместимом индексе делает `rmtree` каталога, который этот же процесс держит
открытым, и на Linux отвязанный файл продолжает отвечать — сервер до конца жизни
выдавал бы результаты из индекса, которого никто не видит и не может обновить.

### 🧱 Что специально сделано «структурно»

Три отказа этой системы — тихие: они ничего не роняют, а просто незаметно ухудшают
выдачу. Поэтому каждый закрыт конструкцией, а не памятью разработчика:

- **FTS-таблица, разъехавшаяся с `chunks`.** Синхронизируется триггерами в схеме,
  а не вызовами на местах.
- **`Searcher`, держащий векторы «до» переиндексации.** Инвалидация живёт в
  `Refresher` и происходит сама. Плюс `chunks.id` объявлен `AUTOINCREMENT`, и это
  не украшение: обычный `INTEGER PRIMARY KEY` — это rowid, SQLite берёт
  `max(rowid)+1`, поэтому id, освобождённые при перезаписи файла, достаются потом
  **другим** чанкам. Буфер «до» тогда отранжировал бы чанк A, а выдача подставила
  бы под его оценку текст чанка B — неверный ответ, а не отсутствующий. С
  `AUTOINCREMENT` id не выдаётся повторно никогда, и вся гонка сводится к
  исчезнувшим id, которые поиск и так отбрасывает.
- **Индекс, собранный другой версией.** Сервер проверяет совместимость при
  открытии и отказывается работать с понятным текстом, вместо того чтобы отвечать
  из файла, который фоновое обновление уже удалило у него из-под рук.
- **Фоновый поток, умерший молча.** Недоступная Ollama — рядовой случай, а не
  экзотика; текст ошибки попадает в `index_status().last_error`.

## 🛠️ Разработка

```bash
$PY -m pytest                                    # 266 тестов, ~7 секунд
$PY -m mypy
$PY -m ruff check .
```

Флаги (`--strict`, набор правил, длина строки) закреплены в `pyproject.toml`, чтобы
«тесты зелёные, линтер чист» значило одно и то же на любой машине и в CI. Те же три
команды гоняет `.github/workflows/code-search.yml` на Python 3.10 и 3.13 при каждом
изменении в `mcp/code-search/`.

`$PY` — интерпретатор, в котором стоят `pytest`, `mypy`, `ruff` и `pyyaml` (последний
нужен только харнессу качества и его тестам; версии — в `requirements-dev.txt`). В системном Python их может не быть, и на дистрибутивах с
PEP 668 доставить их туда нельзя; подойдёт любой venv или отдельный дистрибутив
вроде Anaconda:

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
PY=.venv/bin/python
```

**На сам сервер это не влияет:** ему нужна только стандартная библиотека, поэтому
он ходит под системным Python.

Тесты не требуют Ollama: эмбеддер везде подменяемый, весь набор проходит за 9 секунд,
и ни один тест не пропускается — внешних условий у них нет.

### 🧪 Замеры качества

Числа выше сняты на двух наборах, размеченных вручную по `Project1`: 20 запросов
для разработки и 40 отложенных. **Самих наборов в репозитории нет** — и запросы, и
пути в `expect` описывали внутренности закрытого проекта. Что осталось —
`eval/holdout_results.json`: 40 записей вида `{id, kind, ranks, seconds, tokens}`.
Из них пересчитываются все опубликованные величины (Recall@k, MRR@k, разбивка по
видам, латентность, токены выдачи); о том, что именно спрашивали, в файле нет
ничего. Отложенный набор был **отыгран один раз**, 31.08.2026.

Воспроизводится, таким образом, методика, а не набор. Разметка своего набора —
единственная часть, которую нельзя ни у кого взять: «верный ответ» определён только
внутри конкретного проекта. Формат описан и работает в `eval/queries.example.yaml`,
размеченном по коду самого code-search:

```bash
python3 eval/harness.py /путь/к/проекту                      # eval/queries.example.yaml
python3 eval/harness.py /путь --queries мой_набор.yaml
python3 eval/harness.py /путь --queries мой_holdout.yaml --unblind --save out.json
```

Файл с `holdout` в имени харнесс без `--unblind` трогать откажется — защита от того,
чтобы отыграть отложенный набор случайно. `--save` пишет только замеры, без текстов
запросов: артефакт замера не должен утаскивать за собой содержимое проекта.

Харнесс печатает Recall@{1,3,5,10} и MRR@10 по трём режимам (`lexical`, `vector`,
`hybrid`), разбивку по видам запросов, латентность, объём выдачи в токенах и ранги
по каждому запросу отдельно.

Архитектурные инварианты и границы компонентов собраны в
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), а воспроизводимый процесс разработки —
в [CONTRIBUTING.md](CONTRIBUTING.md).

## ⚠️ Известные ограничения

- **Запросы к тестам не работают** (0.00 полноты). См. выше; нужен размеченный набор.
- **Номера строк устаревают** вместе с индексом. `stale: true` об этом предупреждает,
  но `file_hash` в выдаче стоит сверять, если правки шли прямо сейчас.
- **Первая индексация — десятки минут.** Внутри вызова инструмента она не делается
  никогда: это повесило бы клиент. Сервер вместо этого говорит, какую команду запустить.
- **По умолчанию только `.py`, `.rst`, `.md`.** Остальные языки подключаются флагом
  `--suffix`, но качество на них не измерялось ни разу, и нарезка у них грубее —
  без имён функций и сигнатур, то есть без половины того, на чём держится
  ранжирование. Сколько файлов отброшено, индексатор печатает всегда, так что
  молчаливым этот пробел больше не бывает.
- **Первый запрос после простоя медленнее.** Ollama выгружает модель; `keep_alive=30m`
  это сдвигает, но не отменяет — холодный эмбеддинг 2.67 с против 0.092 с тёплого.
